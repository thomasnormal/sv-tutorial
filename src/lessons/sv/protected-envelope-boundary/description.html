A protected envelope is transformed before the ordinary SystemVerilog source is analyzed. This lesson uses Mox's comment-form //pragma protect ingress to keep a same-buffer opaque payload out of the design's syntax tree.

Exercise

Add the matching end_protected marker. With no protected keyring, Mox does not decrypt the payload; it replaces the opaque envelope and compiles the public wrapper. The finished testbench prints PASS: opaque protected wrapper.

//pragma protect begin_protected
//pragma protect data_block
opaque_payload
//pragma protect end_data_block
//pragma protect end_protected

Keep this example within one source buffer. The landed callback path diagnoses an active envelope when an included buffer ends, so this tutorial does not claim that a protected envelope may begin in one file and end in another.

IEEE 1800-2023 §§34.2, 34.3, 34.4, 34.5.3, and 34.5.4 define protected regions, their transformation before analysis, the protect pragma, and the begin_protected/end_protected delimiters. Decryption requires the proper key; this lesson intentionally demonstrates Mox's no-key opaque boundary instead of decryption.

What landed in Mox

Mox commit c3799f427f1 routes active comment-form protected envelopes through the existing callback. The browser's Run action uses the pinned WASM runtime. Xcelium's reference receipt is intentionally retained as a reference-only failure because it attempts protected-envelope decryption without a key; this lesson does not present the comment-form wrapper as cross-simulator parity.
