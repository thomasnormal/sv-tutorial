The SRAM testbench repeats the same two jobs: compute a value immediately, or wait for a clock while driving a bus. Which helper should own each job? A function returns a value without consuming simulation time; a task can wait for clock edges and use output arguments.

function: data in ──► value out       (zero time)
task:     pins in ──► clock edge ──► pins out  (time advances)

The reusable shapes are:

function automatic <return_type> check (<input> value);
  // compute and return a value
endfunction

task automatic drive (<input> request, <output> result);
  // wait, drive, or sample signals
endtask

automatic gives each call its own local storage, so two calls cannot overwrite one another. A task does not use a return value; an output argument carries a result back to the caller.

In this SRAM bench, parity_check is the zero-time function. write_word and read_word are timing-aware tasks that use the shared mem_if from the previous Interfaces lesson.

write_word: drive we/address/data ─► rising edge ─► release we
read_word:  drive address          ─► rising edge ─► capture rdata

Waiting for @(posedge clk) and then #1 lets the DUT update before the helper samples or releases a signal. Driving and sampling exactly on the edge would race the DUT's own always_ff block.

Open tb.sv and implement the three routine stubs:

  • parity_check(d) — return 1 when d has an odd number of set bits; reduction XOR (^d) computes it.
  • write_word(vif, addr, data) — drive one write, wait one rising edge, then de-assert we.
  • read_word(vif, addr, data) — set the address, wait one rising edge, then capture rdata.

These are the helper routines a UVM driver uses internally. In Part 3 the driver wraps the same protocol in a class method that receives transactions from a sequencer.

The testbench writes and reads three addresses, prints each result and parity, and emits PASS only when every expected value matches.
