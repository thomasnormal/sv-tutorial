Assertions are most useful when they stay beside the design they check without becoming part of the design's source. A bind statement attaches a checker to an existing module from outside that module, so the same counter RTL can be reused in simulation, synthesis, and verification.

The pattern

module <checker>(
  input logic clk,
  input logic <signals>
);
  // properties and assertions
endmodule

bind <target_module> <checker> <instance> (
  .clk(clk), .<signal>(<signal>)
);

The checker declares ports for the signals it observes. The bind names the target module, creates one checker instance for each target instance, and connects those ports to signals in that target. The target module stays unchanged.

What the bound checker samples

t0rst_n=0, count=0disable iff (!rst_n) ignores the reset edge

t2count=1; the next NBA prepares 2count == $past(count) + 1 compares 1 with the prior sample 0
t5en=0, count=4no new increment obligation; the target holds its value
t7rst_n=0; reset drives count to 0 after the edgethe checker is disabled while reset is asserted

Concurrent assertions read sampled values before the counter's nonblocking assignment takes effect. The non-overlapping |=> therefore checks the updated count on the following edge. Because the bind targets the module name, every counter instance receives its own checker with that instance's local signals.

Testbench

The testbench drives the target counter through three phases and prints the observed values. The final PASS is printed only when the counter behavior is correct; the bound assertion is an additional check attached without changing the target module.
