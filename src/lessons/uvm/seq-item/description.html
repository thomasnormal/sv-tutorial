one SRAM operation
┌─────────────────────────────┐
│ mem_item                    │
│ rand we, addr, wdata        │  stimulus
│      rdata                  │  observed result
└──────────────┬──────────────┘
               ▼
       sequence → driver → SRAM pins

A sequence item is one typed transaction object for the SRAM. It keeps the operation's stimulus and observed result together so later UVM components can pass the same object from a sequence through a driver. In uvm/reporting, the test's run_phase controlled when work happened; now that phase has a concrete object to create and report.

The general shape is:

class <name> extends uvm_sequence_item;
  rand <type> <stimulus_field>;
  <type> <result_field>;
  `uvm_object_utils_begin(<name>)
    `uvm_field_int(<stimulus_field>, UVM_ALL_ON)
  `uvm_object_utils_end
  constraint <name> { <legal_values>; }
endclass

Fields marked rand are the stimulus a sequence may vary; rdata is a non-random result captured from the DUT. The constraint in this example gives the item a read-only default. The factory registration macros make the same object visible to UVM's factory and field automation; they are the bookkeeping around the transaction object.

Open mem_item.sv and add three rand fields for we, addr, and wdata, one non-random rdata, their field macros, and the read-only-by-default constraint. The test then randomizes the object, reports it with convert2string(), disables the named constraint, and checks that writes can appear.

Always create items through the factory: mem_item::type_id::create("item"). Factory creation lets a test replace the concrete type without changing sequence code.
