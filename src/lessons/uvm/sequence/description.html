sequence body()          sequencer              driver
  create item ───────────►  arbitration
  start_item ── grant ────►
  randomize / configure
  finish_item ────────────►  get_next_item
                              item_done ───────►

The previous lesson built a mem_item that describes one SRAM operation. A sequence turns that one object into repeatable stimulus. Its key job is to hand each item to the driver through the sequencer without two sequences changing the same item at once. The general shape is:

class <name> extends uvm_sequence #(<item_type>);
  task body();
    <item_type> item = <item_type>::type_id::create("item");
    start_item(item);  // configure while the grant is held
    finish_item(item); // hand it to the driver
  endtask
endclass

The sequence owns the item while it is being configured. The three-step handshake transfers ownership at clear points:

  1. start_item(item) — request access; blocks until the sequencer grants it
  2. Randomize or configure the item while holding the grant
  3. finish_item(item) — hand the item to the driver; blocks until the driver calls item_done()

In this exercise, addr inside {0, 4, 8, 12} is an inline constraint: it limits this item's address to the four aligned locations without changing the reusable mem_item class. Open mem_seq.sv and complete the body() task. A logging driver is already provided — each item you hand off will be printed, so you can see the handshake working immediately.

Sequences are objects (uvm_object), not components — they have no phases. Start them explicitly from a test's run_phase with seq.start(sequencer_handle).
